# Research-to-implementation alignment

This checklist compares the July 30, 2026 capstone paper, *MediScan: A QR-Based Emergency Medical Information System*, with the current mobile/Supabase repository. It does not change the submitted paper or certify the deployed system. Page numbers below are PDF page numbers.

## What the paper actually studied

- Pages 10-11 ask about authorized access, cultural determinants, accuracy, response time, and ISO/IEC 25010 quality. Objective 1 explicitly includes professional license verification, liveness, RBAC, and audit logging.
- Pages 12 and 39-40 include responder scanning, BLE/relay sync, professional verification (FR-008), RBAC (FR-009), a Laravel admin dashboard (FR-011), and audit logging (FR-012). Professional editing is part of the study, not merely an optional feature.
- Pages 87-88 report a heuristic evaluation by **three** licensed specialists. The clinical update module scored 4.67/5 and the overall mean was 4.07/5. These are subjective evaluation results, not proof of clinical accuracy, security, or comparative speed.
- The paper did not test MediScan against Apple Medical ID or Android Emergency Information. The README's comparative retrieval question is a proposed follow-up question.

## Suggested evaluation protocol

1. Create a fixed fictional emergency profile with an allergy, medication, condition, transfusion preference, and contact. Use the same facts in each comparison system. Never use real patient data in demonstrations.
2. Recruit responders or clinically trained participants; record their role and familiarity with each interface. Have each participant complete both conditions in counterbalanced order: MediScan on-phone QR and the platform's native emergency-information flow. Treat Android and iOS as separate strata rather than assuming identical lock-screen behavior.
3. From a standardized start state, measure time to locate each critical field, total actions, completion, wrong/missed interpretations, and whether help was needed. Test offline on-phone QR separately. Test printed dynamic cards as an online workflow.
4. Separately evaluate professional review and editing: application submission, authorized approval, permission denial, patient consent/relay, edit attribution, and audit visibility. Do not mix these outcomes with the speed comparison.
5. Report participant count, device/OS, task order, missing data, and limitations. State that a simulated retrieval task does not establish clinical outcome improvement.

## Decision for the current build

Keep professional verification, admin review, and professional editing as **secondary but in-scope** capabilities while the July 2026 paper's original objectives remain the reference. Prioritize a safe emergency-summary disclosure boundary and a working Supabase review-to-edit path. If the project is formally re-scoped to retrieval only, revise the objectives and requirements before removing those features, and present the old evaluation as historical rather than evidence for the reduced system.
